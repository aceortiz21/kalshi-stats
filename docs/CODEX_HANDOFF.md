## Historical Replay Audit

historical_replay.py currently replays only:

- GRID_V1
- TAIL_V1

It does not currently replay:

- MAIN_TRIGGER
- MAIN_CONTEXT
- MICRO_MULTIPLIER
- generated challengers

Historical replay uses historical_market_features.

Entry uses sampled historical ask prices.

Exits walk later sampled historical bid observations.

Settlement result is not read until after the post-entry path has
been traversed.

No direct replay lookahead was found.

Important replay limitations:

- approximately one-minute historical sampling
- no historical full-depth book
- no true historical IOC latency
- no queue position
- no historical partial-fill modeling
- no intra-minute TP/SL ordering

historical_market_features contains a result column.

Replay itself does not use that field for entry decisions, but
this is a major future ML leakage hazard.

Future ML must use an explicit feature whitelist.

Never use SELECT * for model features.

## Adaptive Research Audit

Adaptive V1 only incorporates replay outcomes satisfying:

exit_ts < current signal_ts

No direct chronological leakage was found.

Its main weakness is statistical: mean ROI is unstable for
asymmetric binary-contract returns.

Adaptive V2 also enforces completed evidence before decisions.

V2 operates on settlement strategies and estimates win
probability using Beta-Binomial style evidence.

It compares conservative probability estimates against
fee-adjusted break-even probability.

Important limitation:

strategy-level observations are currently treated too much like
independent observations.

Many strategy trades may share:

- the same market
- the same side
- the same underlying opportunity

Therefore effective sample size can be overstated.

Future scoring/adaptive work must increasingly distinguish:

- strategy rows
- unique markets
- unique market/side episodes
- shared signal episodes

## PaperBroker Audit

PaperBroker uses approximately:

- $10 virtual starting cash per strategy
- $1 trade notional per signal

These independent accounts are research experiments.

Their aggregate P&L is not a deployable portfolio.

Entry currently uses the first topbook snapshot between:

signal_ts_ms

and:

signal_ts_ms + 2000

If the first observed ask exceeds the IOC limit, the trade becomes
IOC_NO_FILL.

Entry consumes only displayed best-level ask liquidity.

Partial fills are possible.

The broker does not walk multiple order-book levels.

TP:

- triggers when observed bid reaches/exceeds target
- fills at target
- queue position remains unknown

STOP:

- triggers on observed bid
- executes at observed bid
- allows adverse slippage/gaps

SETTLEMENT:

- closes at 1 or 0
- settlement fee currently modeled as zero

## CRITICAL VERIFIED ISSUE

The first Codex audit confirmed a stale/restart PaperBroker
fidelity problem.

PaperBroker does not have a general wall-clock freshness guard
when discovering new signals.

If PaperBroker is offline while upstream collectors continue
recording features/signals, restarting PaperBroker can create new
paper trades from historical backlog.

Those trades are retroactive and must NOT count as genuine
live-forward paper execution evidence.

### GRID_V1 / TAIL_V1

These families use paper_scan_cursors.

If PaperBroker stops while market_sync continues, cursor lag can
cause old feature snapshots to be processed after restart.

Stale rows should advance the cursor but must not create trades.

### Main / Micro paths

MAIN_TRIGGER
MAIN_CONTEXT
MICRO_MULTIPLIER
and any live-discovery micro family

do not all share GRID/TAIL's cursor architecture.

They can query historical rows after the strategy/account start
and rely on unique signal keys.

Equivalent freshness protection is required there too.

## Immediate Required Fix

Before beginning ML work:

1. add a PaperBroker live-signal freshness guard;
2. stale rows must never create new paper trades;
3. GRID/TAIL cursors must still advance past stale rows;
4. main/context/micro paths need equivalent protection;
5. fresh behavior must remain unchanged;
6. preserve all existing historical/paper evidence;
7. do not reset accounts.

Required focused regression tests should cover:

- stale GRID rows produce no signal/trade
- fresh GRID rows still work
- GRID cursor advances over stale rows
- stale TAIL rows produce no signal/trade
- TAIL cursor advances over stale rows
- stale MAIN_TRIGGER / MAIN_CONTEXT signals are ignored
- stale MICRO signals are ignored
- fresh versions of those paths continue working

Use a named freshness constant/configuration rather than scattered
magic numbers.

The exact threshold should be selected from actual broker loop and
timestamp behavior.
