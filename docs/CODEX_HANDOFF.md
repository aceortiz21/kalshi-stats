# Historical Replay Audit

historical_replay.py currently replays only:

GRID_V1
TAIL_V1

It does NOT currently replay:

MAIN_TRIGGER
MAIN_CONTEXT
MICRO_MULTIPLIER
generated challengers

Replay uses:

historical_market_features

Entry behavior:

- sampled historical ask
- approximately 1-minute feature granularity

Exit behavior:

- walks subsequent sampled historical bids
- TP/SL evaluated on future sampled rows
- settlement result read only after the post-entry path has
  been traversed

No direct lookahead was identified in the replay.

Important execution limitations:

- no historical full-depth book
- no real historical IOC latency
- no queue position
- no historical partial-fill simulation
- no intra-minute TP/SL ordering
- sampled rather than tick-level exit paths

Entry fee uses the PaperBroker taker fee estimate.

TP/stop exits also use taker fee estimates.

Settlement exit fee is currently modeled as zero.

# Historical Feature Leakage Hazard

historical_market_features contains a result field on each row.

historical_replay.py does NOT select/use that field when making
decisions.

Therefore no current replay leakage was identified.

However, this is a major hazard for future ML.

Any ML dataset MUST use an explicit feature whitelist.

Never use:

SELECT *

for ML training features.

The settlement result may be used only as the training label
and must never enter the model input matrix.

# Adaptive V1 Audit

historical_adaptive.py uses only replay trades satisfying:

exit_ts < current signal_ts

before adding them to selector evidence.

No direct chronological leakage was identified.

V1's problem is statistical.

It ranks heavily from historical mean ROI.

Cheap binary contracts can produce rare extreme winners that
dominate mean ROI while repeated normal losses destroy the
portfolio.

V1 therefore failed despite respecting chronology.

# Adaptive V2 Audit

historical_adaptive_v2.py currently operates only on replay
strategies ending in:

:settle

Break-even probability is approximately:

(entry_notional + entry_fee) / contract_count

The selector uses Beta-Binomial style probability estimates.

It maintains:

- lifetime evidence
- recent-window evidence

It computes conservative probability bounds and compares them
against fee-adjusted break-even probability.

FAST and STRICT use different evidence/confidence thresholds.

Chronological evidence is restricted to completed trades with:

exit_ts < current signal_ts

No direct time leakage was identified.

Important limitation:

strategy observations are treated as independent Bernoulli
samples.

They are NOT currently clustered by:

- market
- market/side episode
- shared underlying opportunity

Therefore effective sample size can be overstated.

This must be considered in future adaptive/ML research.

# Position Sizing Limitation

Adaptive historical position scaling linearly rescales baseline
replay results.

That is acceptable only as a research approximation at small
size.

Larger position sizes cannot assume proportional execution
because historical replay lacks:

- full depth
- realistic market impact
- realistic multi-level fills
- real IOC latency

Do not interpret $5/$10 historical scaling as execution proof.

# PaperBroker Audit

PaperBroker uses one independent paper account per registered
strategy.

Current paper experiments generally use:

starting_cash ~= $10
trade_notional ~= $1

These accounts are experimental.

Their aggregate equity is NOT one finite deployable portfolio.

## Entry behavior

Entry uses the first topbook_snapshots row found between:

signal_ts_ms

and:

signal_ts_ms + 2000 ms

The first observed book is treated as the IOC opportunity.

If the first observed ask exceeds the signal limit:

IOC_NO_FILL

If available best ask depth is limited:

partial fill is possible

Entry currently consumes only best ask size.

It does not walk multiple price levels.

It also does not continue searching later book observations
inside the two-second window after the first unacceptable
observation.

## Exit behavior

TP:

- triggers when observed bid reaches/exceeds target
- fills at target price
- queue position remains unknowable
- fee is conservatively modeled using taker-rate estimate

STOP:

- triggers on observed bid crossing the stop
- executes at actual observed bid
- adverse gap/slippage is possible

Exit partial fills may continue over subsequent topbook rows.

SETTLEMENT:

- closes residual contracts at 1 or 0
- settlement fee currently modeled as zero
- paper close timestamp uses broker processing time rather than
  the market settlement timestamp

# CRITICAL PAPERBROKER ISSUE

The audit CONFIRMED a stale/restart fidelity bug.

PaperBroker currently has no general wall-clock freshness guard
when discovering new paper signals.

If PaperBroker is offline while upstream collectors continue
recording signals/features, restarting PaperBroker may create
paper trades from historical backlog.

Those trades would be retroactive and therefore should NOT be
treated as true live-forward paper evidence.

This issue must be fixed BEFORE relying heavily on future
prospective evidence.

## GRID_V1 / TAIL_V1

These families use:

paper_scan_cursors

If the cursor lags during a PaperBroker outage, restart can
consume old market_feature_snapshots and create retrospective
paper signals.

## MAIN / MICRO families

MAIN_TRIGGER
MAIN_CONTEXT
MICRO_MULTIPLIER
MICRO_LIVE_DISCOVERY

do not currently use the same family scan-cursor mechanism.

They query rows since the strategy/account forward start and
rely on unique signal keys.

Therefore they may also discover historical backlog after a
PaperBroker-only outage.

# Required Stale-Signal Fix

The next implementation task should be a SMALL PaperBroker
fidelity patch before ML work.

Goal:

PaperBroker must create new paper trades only from sufficiently
fresh live-forward signals.

Stale rows may be inspected/consumed for cursor advancement,
but MUST NOT create new paper trades.

The implementation should avoid repeated rescanning of stale
rows.

The exact freshness threshold should be chosen after inspecting
the current PaperBroker event loop and timing behavior.

A rough expected threshold is on the order of a few seconds,
not minutes.

Required regression coverage should include at least:

1. stale GRID/TAIL feature snapshots do not generate new paper
   trades after restart;

2. fresh GRID/TAIL feature snapshots still generate normal
   signals;

3. cursors advance past stale GRID/TAIL rows so they are not
   rescanned forever;

4. stale MAIN_TRIGGER / MAIN_CONTEXT inputs do not create
   retroactive paper trades;

5. stale MICRO inputs do not create retroactive paper trades;

6. currently fresh inputs continue to behave exactly as before.

Do not delete old paper evidence while fixing this.

Do not reset existing strategy accounts.

# Correlation / Evidence Audit

Current sample_n is largely strategy-trade count.

unique_markets is also tracked.

However, the research system does not yet consistently track
independent market/side episodes for scoring.

Many strategies may fire from the exact same underlying
market-side opportunity.

Therefore:

100 strategy trades

does not imply:

100 independent observations

Future statistical work should distinguish:

- strategy rows
- unique markets
- unique market/side episodes
- shared signal episodes

This applies to:

- score snapshots
- challenger evaluation
- adaptive selection
- future ML-derived trading evaluation

# Documentation Discrepancies Found

The code audit found several places where documentation should
eventually be clarified.

1. Historical replay currently covers only GRID_V1 and TAIL_V1.

2. Adaptive V1/V2 therefore operate on zoo replay results, and
   V2 further restricts to settlement strategies.

3. BRTI is already used in some prospective research tables,
   not merely planned for future modeling.

4. Public trade collection exists for backfill/CLI usage, but
   the always-on live finalization path intentionally skips
   bulk public trade download. The audited DB had trades=0.

5. Counts in documentation are illustrative and become stale
   as live research runs.

6. paper_engine_snapshot.json is comprehensive for PaperBroker
   state but does not contain every raw prospective/micro/
   shadow table in the entire database.

These are documentation clarifications rather than emergency
bugs.
